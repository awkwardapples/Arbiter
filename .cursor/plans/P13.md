# P13 plan: Zetaris USL `vendor_risk`, for real

**Phase:** plan. **Branch:** `p13-usl` (checked out, tracking `origin/main`). **Marker:** `p13`. `.cursor/ACTIVE_PASS` is `13 plan`.

This lane is attended. After approval, tests land first, then the offline code, then the live procedure. Every create, drop, deploy, activate, register, update or `onboard --yes` waits for an explicit **go**. `COMPILE USL` without `DEPLOY` stores nothing and is the debug tool. The API key is never printed. Port 8889 is never called. `.env` is never opened; you set `ZETARIS_QUERY_LAYER=usl` yourself.

## Goal

Turn the failed one-shot `COMPILE USL` into a deployed, activated `vendor_risk` model over the onboarded sources: business descriptions, five DQ rules registered and run inside Zetaris, and the public CISA KEV feed instead of the repo snapshot. Live mode then queries that model. The Planner’s model path reads a compact catalogue taken from `LOAD USL`, and one new `Q_VENDOR_360` query shows the same join on DuckDB and on the USL. `docs/ZETARIS_USL.md` records measured numbers only, including the custom-pipeline versus USL comparison.

## Decisions in this plan

1. **Bisect before rewriting `03_usl.sql`.** The committed DDL stays as it is until the attended bisect (§ Bisect) names the failing token. Fixes follow the verified SIC scripts: one `COMPILE` statement, each `CREATE TABLE` on its own line, fully qualified names after that, `COALESCE` on NOT NULL keys, explicit `CAST`s, descriptions in single quotes.
2. **`RUN DQ TABLE <fqn>` first.** That is the form in the pass spec and in `01_sic_usl_create.sql` / `02_sic_edgar_usl_create.sql`. If the instance requires a rule name (commands guide §14.6), switch to one `RUN DQ <rule> TABLE <fqn>` per rule from `dq_rules.yaml` and record the change in the report.
3. **Probe compiles use `usl_probe` and omit `DEPLOY`.** They store nothing. `vendor_risk` is deployed only after the working 10-table DDL is known, and only after **go**.
4. **`Q_VENDOR_360` returns one row for one vendor.** Sample data is 32 vendors, 32 contracts (every `clm_supplier_ref` matches), 32 submissions (one each), and 2 components. The statement inner-joins vendor, contract and submission, and left-joins `vendor_component` and `kev_vuln`. An inner join to components would drop the 30 vendors with none. The KEV predicate is the one already in `Q_COMPONENT_KEV`.
5. **Live KEV and DuckDB will not hash-match on KEV columns.** DuckDB keeps the snapshot. `Q_COMPONENT_KEV` and `Q_KEV_BY_PRODUCTS` stay in `SKIP_QUERIES`. `Q_VENDOR_360` gets its own check: every non-KEV column and `component_count` equal; `kev_cve_count` on Zetaris is greater than or equal to DuckDB; `latest_kev_date` on Zetaris is greater than or equal to DuckDB when both are present. Both sides are stored in `P1-B_parity.json`. `all_green` requires that check. `app/data/duckdb_backend.py` is outside this lane, so the snapshot stays the mirror’s source.
6. **A renamed USL column is aliased back.** If bisect rejects `text`, `status`, `version` or `category`, the new name exists only in the USL. `ACTIVATE` aliases the view column onto it. A `sql_usl` override aliases it back to the registry column. DuckDB and the views keep the original name. No override is added unless a rename actually happens.
7. **The committed model JSON is only written by `model --export`.** It is a scrubbed `LOAD USL` payload. It is not authored by hand. `load_model()` is called on the LLM planning path only, so a missing file does not change the deterministic plan or sample-mode e2e.
8. **Trace fields stay in the summaries.** `TraceEvent` has no slot for `usl_model_sha256`. `app/schemas/trace.py` is outside this lane. The event `PlannerAgent` / `usl_catalogue` carries `usl_model_sha256=<hex>` in `input_summary` and `tokens=<n>` in `output_summary`.
9. **Screenshots are captured by you**, with no key on screen, into the three paths in § Files. This pass does not generate those images.
10. **Descriptions below are the text that will be sent**, if you approve them. They avoid apostrophes so the quoted SQL stays simple.

`Q_VENDOR_360` in `queries.yaml`:

```sql
SELECT v.vendor_id,
       c.status AS contract_status,
       c.dpa_signed,
       c.hosting_region_clause,
       c.breach_notification_hours,
       s.patch_sla_critical_days,
       COUNT(DISTINCT comp.component_id) AS component_count,
       COUNT(DISTINCT k.cve_id) AS kev_cve_count,
       MAX(k.date_added) AS latest_kev_date
FROM {T.vendor} v
INNER JOIN {T.contract} c ON v.clm_supplier_ref = c.supplier_ref
INNER JOIN {T.submission} s ON s.vendor_id = v.vendor_id
LEFT JOIN {T.vendor_component} comp ON comp.vendor_id = v.vendor_id
LEFT JOIN {T.kev_vuln} k
  ON lower(k.vendor_project) = lower(comp.vendor_project)
 AND lower(k.product) LIKE concat('%', lower(comp.product), '%')
WHERE v.vendor_id = :vendor_id
GROUP BY v.vendor_id, c.status, c.dpa_signed, c.hosting_region_clause,
         c.breach_notification_hours, s.patch_sla_critical_days
```
