# Nightshift lane routing: human observations

This file is the human-written companion to `docs/evidence/nightshift_proof.json`. It records what the operator checked by hand on the development machine on 24 October 2026. Code did not observe these facts.

The proof file is machine-generated by `python run.py llm proof`. Its `deviations` list is derived only from the two receipts it contains.

Written from the operator's account and reviewed by the operator before commit.

## Lane design

| Lane | Arbiter sends | Original target | Bound in the Nightshift fleet |
|---|---|---|---|
| fast | `meterless/fast` | `nvidia/nemotron-3.5-lightning-30b-a3b` | `nvidia/nemotron-3.5-lightning-30b-a3b` |
| deep | `meterless/deep` | `nvidia/nemotron-3-super-120b-a12b` | `nvidia/nemotron-3.5-super-vl-120b-a12b` |

Arbiter sends routing modes, not model ids (`METERLESS_MODEL_FAST=meterless/fast`, `METERLESS_MODEL_DEEP=meterless/deep`). Nightshift picks the model.

## Observations

1. **Super 3 120B is not entitled.** The deep lane originally targeted `nvidia/nemotron-3-super-120b-a12b`. A direct curl to that model through Nightshift returns HTTP 404: "Function ... Not found for account ...". The NVIDIA account is not entitled to that model, so the deep lane was re-bound to `nvidia/nemotron-3.5-super-vl-120b-a12b`, which is entitled and returns completions.
2. **The fleet lanes are bound and ready.** The Nightshift UI (Lanes/Fleets) binds the fast lane to `nvidia/nemotron-3.5-lightning-30b-a3b` and the deep lane to `nvidia/nemotron-3.5-super-vl-120b-a12b`. The NVIDIA key is accepted for both. The Monitor tab shows both lanes ready. A direct curl to `nvidia/nemotron-3.5-lightning-30b-a3b` returns a completion, so Lightning is entitled.
3. **An app rule overrides the lanes.** Nightshift's Default app rule matches the `meterless-app: arbiter` header and forces a bound mode before the fleet's lanes are consulted. The Console does not expose a way to unbind this rule. This is a Nightshift build limitation.
4. **Restart attempts did not change routing.** The operator tried:
   - a Cockpit restart;
   - a daemon restart;
   - logging out and back in;
   - saving a fresh minimal fleet (`my-fleet`) with both lanes bound correctly. The daemon refused the save with "The daemon refused this.", and the UI gave no reason.

   Re-activating the saved `imported-v2` fleet did not change the routed model.

## What the receipts show

Three proof runs were made on 24 October while the operator changed Console settings. The earlier two are kept in `docs/evidence/history/`. Every run returned Nemotron completions with Nightshift receipts.

| Run | File | fast | deep |
|---|---|---|---|
| 1 (03:37Z) | `history/nightshift_proof-run1.json` | `bound_mode: deep`, coerced fast→deep, Super VL | not coerced, Super VL |
| 2 (04:01Z) | `history/nightshift_proof-run2.json` | `bound_mode: auto`, coerced, Super VL | `bound_mode: auto`, coerced, Super VL |
| 3 (04:05Z) | `nightshift_proof.json` | `bound_mode: auto`, coerced, Lightning | `bound_mode: auto`, coerced, Super VL |

In run 3 both lanes are in `auto` mode, which picks the model per request. That run's tiny prompts landed on Lightning (fast) and Super VL (deep). In the first live example attempt, a 4,986-character planner prompt sent on the deep lane was coerced the same way and landed on Lightning, which returned HTTP 502 `nvidia/nemotron-3.5-lightning-30b-a3b_empty_response`. Lane separation is therefore not guaranteed while the app rule is in force.

## Conclusion

The proof records what actually ran. The fleet's lane bindings are correct, but the app rule overrides them, and the Console offers no way to remove it. The daemon and its lane routing are outside this repository and were not changed. Every completion is a Nemotron model served through Meterless Nightshift.
